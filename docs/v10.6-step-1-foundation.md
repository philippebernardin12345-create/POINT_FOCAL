# V10.6 — Étape 1 : Fondation Persistante

## Objectif

Construire le socle technique persistant V10.6 permettant de sécuriser :

- Le root réel persistant (UUID dans `v106_runtime_state.root_user_id`)
- La phase `LEADER_LAUNCH` / `NORMAL_OPERATION`
- Le seuil de 50 leaders
- L'attribution globale du sponsor avec maximum 2 directs
- L'atomicité et la concurrence PostgreSQL
- La journalisation de la transition de phase
- Un système de migrations versionnées
- Des transactions réutilisables

## Fonctions SQL créées

### `v106_assign_global_sponsor(p_sponsor_id UUID, p_child_id UUID)`

1. Verrouille `users` WHERE id = `p_sponsor_id` (FOR UPDATE)
2. Verrouille `users` WHERE id = `p_child_id` (FOR UPDATE)
3. Vérifie `sponsor ≠ child`
4. Recherche atomiquement le premier slot libre (1 puis 2)
5. Insère l'attribution
6. Lève une exception `sponsor_full` si les 2 slots sont occupés
7. Retourne `slot_no`

### `v106_transition_phase_to_normal_operation()`

1. Verrouille le singleton (FOR UPDATE)
2. Retourne `already_normal_operation` si déjà en `NORMAL_OPERATION`
3. Recalcule `leader_count` depuis `users.is_leader` (colonne réelle)
4. Met à jour `leader_count` dans le singleton
5. Retourne `threshold_not_reached` si `leader_count < 50`
6. Bascule `phase = NORMAL_OPERATION`
7. Insère un événement d'audit (ON CONFLICT DO NOTHING → idempotent)
8. Retourne `transitioned`

## Calcul des leaders

```sql
SELECT COUNT(*) FROM users WHERE is_leader = TRUE;
```

La colonne `is_leader` est présente dans le schéma réel de `users` (type boolean).  
`users.is_root` reste **LEGACY** et n'est pas utilisé pour ce calcul.

---

## Root V10.6

- `root_user_id` dans `v106_runtime_state` est le root V10.6 persistant.
- `users.is_root` reste en place et inchangé (legacy).
- `setRootUser(userId)` : définit `root_user_id` dans le singleton.
- `resolveRootUser()` : retourne l'utilisateur via `root_user_id`, repli sur `is_root = TRUE` si non défini.

## Garanties de non-destruction

- Aucune table existante n'est supprimée.
- Aucune colonne legacy n'est modifiée.
- Aucune donnée métier n'est modifiée.
- Aucun backfill automatique.
- Toutes les tables V10.6 utilisent `CREATE TABLE IF NOT EXISTS`.
- La migration se réenregistre via `ON CONFLICT DO NOTHING`.
